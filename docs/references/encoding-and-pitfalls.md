# 编码与落盘规范 · 防复发手册

> 本文件是 2026-09-23 资料库编码缺陷修复（2961 个文件）后的**规范固化**。
> 目标是：**同样的坑不再踩第二次**。
> 配套工具：`scripts/corpus_lint.py`（回归守卫，带 baseline）。

---

## 一、事故复盘：这些缺陷是怎么产生的

### 1.1 唯一的根因

**Windows PowerShell 5.1 + CP936(GBK) 控制台 + 内联中文脚本。**

链条是这样的：

```
Python 脚本源码本来是 UTF-8
   ↓ 但脚本通过 powershell -Command "..." 内联传递，或 heredoc 写盘
PowerShell 5.1 按当前控制台代码页(CP936) 读取/写入字节
   ↓ 中文的 UTF-8 字节序列 (3字节/字) 被当作 GBK 解码
GBK 把 3 个 UTF-8 字节错拼成 1~2 个"汉字"
   ↓ 无法对应的字节 → 私用区字符 U+E000–U+F8FF
落盘 = 乱码 + PUA 字符
```

典型对照：

| 原文 | 乱码（GBK 误读 UTF-8） |
|------|------------------------|
| `日期：` | `鏃ユ湡锛?` |
| `语音转录` | `璇煶杞綍` |
| `简介` | `绠€浠?` |
| `实况` | `瀹炲喌` |

### 1.2 缺陷清单（已全部修复）

| 编号 | 缺陷 | 数量 | 说明 |
|------|------|------|------|
| A | 正文乱码表头 | 828 | 文件正文里被写死的中文行头，形如 `@{page=...}.date)` / `BVID…bvid` |
| B | 乱码小标题 `##璇…` | 855 | `## 语音转录` 被写坏 |
| D | UTF-8 BOM | 2839 | `\xef\xbb\xbf` 开头 |
| E | 缺 frontmatter 起始 `---` | 90 | 首行直接是 `name:` / `title:` |
| C | 正文失效（API 错误页） | 14 | 404/502/Too Large 的正文，需重转录 |
| F | 两份拷贝不一致 | 39+4 | 主库 vs GitHub 镜像 |

### 1.3 为什么"正文里会有中文表头"

早期采集脚本在下载音频时，把响应里的中文标签（`"日期："`、`"BVID："`）直接
**拼进了正文的 print/f-string**，而不是走 frontmatter。一旦控制台编码错，
这些字面量就永久写进了文件。**正文里不该有任何由程序生成的中文表头。**

## 二、硬性规范（R1–R10，必须遵守）

### 文件写入

- **R1｜一切落盘 UTF-8，不带 BOM。**
  Python 一律 `open(..., encoding="utf-8")` / `Path.write_text(..., encoding="utf-8")`。
  禁止依赖默认编码（Windows 上是 cp936）。**永远显式写 `encoding=`。**

- **R2｜禁止用 PowerShell 内联中文写文件。**
  不要 `powershell -Command "echo 中文 > x.md"`，
  不要 `Set-Content`（5.1 默认 ANSI），
  不要 `Out-File`（5.1 默认 UTF-16LE）。
  中文内容一律：**用 Python 脚本写**（脚本文件本身存为 UTF-8，且通过 `-File` 调用，
  不经 `-Command` 字符串）。

- **R3｜控制台脚本先重设 stdout。**
  任何会打印中文/异常文本的诊断脚本，第一行加：
  ```python
  sys.stdout.reconfigure(encoding="utf-8", errors="replace")
  sys.stderr.reconfigure(encoding="utf-8", errors="replace")
  ```
  否则 CP936 控制台遇到 `U+FFFD` 会直接抛 `UnicodeEncodeError` 让脚本崩溃
  （这正是修复过程中"审计脚本自己崩了"的原因）。

- **R4｜不往文件里写"由程序生成的中文标签"。**
  正文只放转录文本本身。元数据全部进 YAML frontmatter。
  禁止在正文出现 `日期：` / `BVID：` / `时长：` / `播放量：` 这类行头。

- **R5｜不用 `>` / `>>` 重定向来收集命令输出再读回。**
  一律让脚本自己 `write_text(..., encoding="utf-8")`。
  （本会话里 ExecCommand 的 stdout 多次为空，重定向到文件是唯一可靠通道，
  但**写文件的那一端必须显式指定 UTF-8**。）

### frontmatter 契约

- **R6｜`date` = 视频发布日（pubdate），不是转录日。**
  `get_video_info()` 的 `pubdate` → `time.strftime("%Y-%m-%d", localtime(pubdate))`。
  绝不允许用 `time.strftime(...)`（当天）兜底，那会让历史视频全部标成今天。
  取不到 pubdate 时写空串并记录告警，**不要静默填今天**。

- **R7｜文件必须以 `---` 开头。**
  每个 `dufu-*.md` 第一个字节就是 frontmatter 起始符。
  缺了它 Obsidian/GitHub 都会把 YAML 当正文渲染。

### API 请求纪律

- **R8｜所有"取钥匙/换令牌"的调用必须在重试循环之外，取一次缓存住。**
  反例（导致 B站 -352 风控，成功率从 250/250 掉到 50/250）：
  ```python
  for attempt in range(N):
      key = get_wbi_key()          # ❌ 每次重试都重新请求 nav 接口
      sign_and_call(key)
  ```
  正例：
  ```python
  key = None
  for a in range(8):               # 只重试"取钥匙"本身
      k = get_wbi_key()
      if k and len(k) >= 32:
          key = k; break
      time.sleep(4 + a * 3)
  if not key:
      raise RuntimeError("no wbi key")
  for attempt in range(N):         # 业务重试复用同一个 key
      sign_and_call(key)
  ```
  同理适用于任何 token / 签名 / 登录态。

- **R9｜-352 是随机风控，不是参数问题。**
  实测 `platform` 取 none/web/android 都是在 50%–66% 概率命中，
  与参数无关。**不要靠换参数绕**，要靠：缓存 key + 失败退避 + 不要高频重复请求。

- **R10｜"确定拿不到"的视频要缓存，不要每天重试。**
  充电专属（充电视频）无法转录 → 写入 `charging_videos.json`，
  采集时 `and bvid not in charging_bvids` 过滤掉。
  14 个 API 错误页同理：沉淀成 baseline，而不是每次采集都撞一遍。

## 三、回归守卫：corpus_lint.py

**每次批量写盘之后必须跑一次。**

```powershell
cd "$env:USERPROFILE\Desktop\独夫之心-修复包"
python corpus_lint.py                  # 对照 baseline 检查
python corpus_lint.py --all            # 连已知/已接受的问题一起看
```

它检查 10 类信号：BOM、非法 UTF-8、U+FFFD、PUA 字符、乱码特征串、
`@{page=...}` 表头、`BVID..bvid` 表头、`##璇` 小标题、正文内写死的中文表头、
CRLF/LF 混用、API 错误页正文。

- 退出码 `0` = 无新增缺陷；`1` = 发现**回归**。
- `corpus_lint_baseline.json` 记录了 15 条"已知且接受"的例外
  （14 个 API 错误页 + 1 个丢失字符），**只有 baseline 之外的才会报警**——
  这是为了避免告警疲劳。
- 新增例外必须**显式** `--update-baseline`，即"我确认这条可以接受"。

> 自测：故意往一个文件里塞一个 PUA 字符，`corpus_lint.py` 必须退出 1。
> 已验证通过。

## 七、第二轮：2026-09-23 二次排查新增的坑

第一轮（编码）修完之后做**独立复核**时又挖出一批问题，一并固化：

### R11｜模块尾部不得再定义同名函数（"兼容 shim"是隐形的破坏者）

`bilibili_transcribe.py` 末尾曾有以下"兼容层"：

```python
def init_logging():
    """no-op for standalone mode, used by daily_scan."""
    pass

def get_wbi_key():
    return get_mixin_key()
```

后果（Python 取**最后一次**定义）：

* 真正的 `init_logging()`（会 `logging.basicConfig`）被降级成空操作；
* 真正带缓存的 `get_wbi_key()` **被完全绕过** —— 即 R8 的修复形同虚设，
  每次调用都重新打 nav 接口，`-352` 风控自然照旧。
* 同一个 `MIXIN_KEY_ENC_TAB` 还被定义了两次（内容相同、无副作用，但极难看）。

**症状**：加了缓存却没有任何效果；"明明改过了还是被风控"。
**排查**：`[m.group(1) for m in re.finditer(r"^def (\w+)", src, re.M)]` → 找重复。
**修法**：删掉 shim，让真正实现生效；需要兼容就改签名，不要覆盖。

> 教训：**任何"看起来无害的兼容层"都要先问一句——它会覆盖谁？**

### R12｜绝不返回"编造的"兜底密钥 / 令牌

同一个函数里还藏着：

```python
except Exception:
    return 'c5f4d2a1e8b7f03c6d9a2e5b8f1c4a7d'   # ❌ 假的 mixin key
```

假密钥不会报错，只会让 `w_rid` 签名**静默错误**，API 返回 `-352` / `请求错误`，
于是你以为是"随机风控"，其实是自己拿错了钥匙。

**修法**：改为 `raise RuntimeError(...)`，让调用方退避重试。

> 教训：凭据类兜底值**只有两种合法形态**：正确值，或显式异常。

### R13｜"两库一致"必须逐文件哈希校验，且裁决要有证据

资料库有两个根（主库 + GitHub 镜像），历史上各自被不同批次改过，
演化出 42 个同名文件内容不同：

* 主库侧 = **完整**正文（但 `date` 误写成批次日 `2026-08-04`、缺 `type`/`warning`）；
* 镜像侧 = 只有**开头约 300 秒**的截断正文（是另一个 ASR 结果，人名/用词略异），
  但 `date` 接近真实发布日期、并带 `type: dialogue` + `warning:`。

裁决过程（可复用）：

1. 逐文件 sha256 比对，列出全部分歧（别只看计数）。
2. 对每对文件计算**归一化正文**的"前缀相似度"——镜像正文 ≈ 主库正文开头时，
   即可判定"镜像被截断"，不是"两种风格"。
3. 语义正误不能靠猜：在**全库**统计各候选词的出现次数
   （例：`梅老师` 4 次 vs `梅儿老师`/`麦老师` 各 1 次 → 后者都是 ASR 变体）。
4. **裁决 = 取内容更完整的一方**；另一方的元数据**抢救**过来；
   被替换的那一版**归档备份**，绝不直接丢。

**最终动作**：以主库完整正文为准，镜像版归档到
`独夫之心-修复包\镜像旧版-被替换稿\`，并保留镜像的 `type`/`warning`。

**分歧的根因与根治**：采集脚本第 6 步原先是

```python
for v in new_videos:                      # ❌ 只镜像"本次新采集的视频"
    shutil.copy2(main/dufu-{bvid}.md, repo/dufu-{bvid}.md)
```

→ 任何**后来**被重新转录 / 编辑 / 补元数据的文件，永远不会同步到镜像，
分歧就这样一天天积累。已改为**全量单向哈希同步 + 同步后校验**
（见 `daily_scan.py` Step 6；验收测试
`修复包\_过程记录\_test_mirror_step.py`：干净→0/0/0，人为截断→自动修复 1/1/0）。

### R14｜`date` 的唯一真值 = B站 API 的 `pubdate`（北京时间）

本次共修 347 个文件的日期（另有 1 个非转录文件跳过）：

* **304 个根本没有 `date` 字段** → 全部补上 API `pubdate`；
* **43 个被写成批次运行日 `2026-08-04`** → 逐条与 API 核对后改写。
  其中 **39 个确实是错的**，但 **4 个视频真的在 08-04 发布** ——
  所以**不能一律改**，必须以 API 为准（这点是本次最重要的教训）；
* **28 个被写成 `1970-01-01`**：这些 bvid 已**无法解析**
  （API 返回 `啥都木有`，视频删除/私密），取不到真值 → **保持原样并记录**，
  绝不猜。本次共 29 个 bvid 无法解析。

**判别小技巧**：同一日期上挂着几十个文件 ≈ 那是一次批量运行日，不是发布日。

**取真值**：`time.strftime("%Y-%m-%d", time.localtime(pubdate))`。
本次逐条与 API 核对，347 个文件全部 `file == api` 通过。

> 注意：取不到的（视频已删除 / 私密）**不要瞎填**——本次有 29 个 bvid
> 返回 `啥都木有`，一律保持原样并记录，等日后有线索再补。

### R15｜改文件时**必须保留原换行符**

本库是 **CRLF**（3692 个文件）。用 `"---\n" + fm + "\n---"` 重装 frontmatter，
会把 CRLF 文件变成"CRLF 正文 + LF 头"的混合文件 —— 正好撞上 lint 的
CRLF/LF 混用检测。

**修法**：从文件里探测 `eol`（`\r\n` 优先），内部用 `\n` 处理，
写回时 `fm.replace("\n", eol)`，并且 `open(..., newline="")` 关闭翻译。
本次 347 个文件**零混合换行**。

### R16｜守卫工具自己也要守规矩

`corpus_lint.py` 原本没做 `sys.stdout.reconfigure` —— 一旦它检测到
`U+FFFD`/PUA 并打印出来，CP936 控制台会直接抛 `UnicodeEncodeError`
**把守卫自己弄崩**（恰好发生在最需要它的时候）。已补上（R3），
并加了 `--root` 用于自测：干净语料必须退 0，注入缺陷必须退 1。

## 十、第三轮（2026-09-27）：frontmatter 元数据与路径卫生

第三轮不再查"编码"，改查 **frontmatter 元数据**，结果又挖出四类坑。
共同的教训是：**编码对了不等于文件对了** —— 字节层干净的文件，元数据层仍可能是错的。

### R17｜绝不"重装"frontmatter：只做原地字符级替换

**事故**：`memory\dufu-BV1APjc6EE3y.md` 的 frontmatter 被整个掏空，
变成 `---␊␊---␊␊# 问答环节…`（头没了，正文完好）。
原因是某个批量脚本把 frontmatter 当**对象**读出来、再 `"---" + fm + "---" + body`
拼回去；一旦解析出空 fm，就会把空值写回去 —— **写坏得悄无声息**。

**规范**：
1. 读文件用 `open(p, encoding="utf-8", newline="")`（R15）；
2. 只对**目标字段**做字符级 splice：
   `raw[:m.start(2)] + new_value + raw[m.end(2):]`；
3. 写回前**断言**：`raw[fence_end:] == out[new_fence_end:]` —— 除
   frontmatter 之外，**任何一个字节都不许变**；
4. 绝不用"解析 → 重组 → 落盘"处理正文。

**为什么这次没被发现**：旧校验只比**正文**哈希、只看"有没有 warning 字符串"，
frontmatter 坏了正文照样通过。**只比正文的校验等于没校验。**

### R18｜两库一致 = **整文件哈希**一致，且清单要对得上

R13 说的是"逐文件比哈希"，第三轮要把口径收紧到**整文件（含 frontmatter）**：

* 同名文件整文件 sha256 必须相同；
* 只存在于一个根的文件必须**在白名单里**（如 `no-git-operations.md` 只放主库）；
* 任一差异即为回归 —— 因为主库/镜像的差异**只可能来自写坏**，
  不可能是"正常的"。

本轮修完：`main-only = 1`（白名单），`hash-differs = 0`。

### R19｜`连麦/问答` 视频**必须**同时带 `type: dialogue` 与 `warning`

采集器本身**不写** `type:` 和 `warning:`（见 `save_transcript`），
这两个字段是**后续富化**加上去的。因此它们是"人工约定"，必须由守卫兜住：

* 标题（或 Gen-A 的 `name:`）含 `连麦`/`问答` → 必须有 `type: dialogue`；
* 必须有一条 `warning:`，正文里要出现 **`独夫之心`**（说明"谁的观点算数"）；
* **不许出现 `联麦`**（错别字，第三轮清了 4 个）；
* 弱化版提示语（只说"建议结合原视频收听"）要升级成完整版
  —— 提示语的全部意义就是"别把提问者的观点算到独夫之心头上"。

**另一种坑**：`change_log_dialogue_warning.csv` 里写着
`added = "type:dialogue + warning"`，但实际**没写 type**（脚本里根本没有
处理 `type` 的代码）。**日志必须记录"实际发生了什么"，而不是"打算做什么"** ——
写完要**回读**取证据。

### frontmatter 的"世代"（重要：不要强行统一）

语料是不同年代的工具写的，frontmatter 有**至少 5 种世代**：

| 世代 | 键 | 数量级 | 备注 |
|------|----|--------|------|
| A（最早） | `name/description/type/date` | ~820 | 没有 `bvid`/`title`，正文常是一整行 |
| B | `type/title/bvid/date/duration/source/status` | ~710 | |
| C | `title/bvid/date/duration/transcribed` | ~590 | |
| D | B + `length` | ~320 | |
| E（现行） | `title/bvid/date/duration/source` | 新增文件 | 可选加 `type`/`warning` |

**结论**：**不要**为了"整齐"去批量重写 3600+ 个文件 —— 风险远大于收益。
守卫只校验：(a) frontmatter 非空且至少有一个身份键；(b) `连麦/问答` 元数据契约（R19）；
(c) 两库整文件一致（R18）。**新文件**一律用世代 E。

### R21｜Whisper 的**错误载荷**绝不许当成转录稿落盘

**事故**：语料里有 **14 个文件**的正文不是讲话，而是 API 的报错 JSON：

```
{"error":{"type":"upstream_error","message":"{\"error\":{\"message\":
\"Request Entity Too Large\",\"type\":\"invalid_request_error\",
\"code\":\"request_too_large\"}}\n"}}
```

成因：兼容 OpenAI 的端点会用 **HTTP 200 + 错误 JSON** 回复，而旧代码
`resp.read().decode()` 拿到什么就当成转录文本写盘 —— 于是"失败"被记成了"成功"。
kb-mcp 把这 14 个识别为 `dead`（不进检索），用户看到的"文件有问题"就包括它们。

**规范（三层防护，缺一不可）**：

1. **读回即校验**：`looks_like_api_error(text)` —— 以 `{"error"` / `{"message"`
   开头的短 JSON，或 < 500 字且含 `upstream_error` / `request_too_large` /
   `Bad Gateway` 等标记的文本，一律视为错误；
2. **超限就切分**：命中 `too_large` 时**不要重试同样的字节**，而是把该分片
   再按 1/4 时长切一遍重发（`transcribe_long_audio` 里的自适应切分）；
3. **落盘前兜底**：`save_transcript()` 第一行就拒绝错误载荷，
   宁可抛异常也绝不写文件。

**误杀防线**：`looks_like_api_error` 的阈值刻意压到 500 字 ——
否则"独夫之心正在评论某网站 Bad Gateway"这种真转录会被当成错误丢掉。

### R22｜ffmpeg 子进程必须有硬超时，且 `-ss` 必须放在 `-i` **前面**

**事故**：重转录 14 个文件时，第 1 个视频（3 小时长）卡了 **25 分钟以上**一动不动。
查进程发现一个 ffmpeg 还在烧 CPU（48 秒 CPU、存活 25 分钟），python 侧 0 CPU 在等。
两个独立的坑叠在一起：

1. **`-ss` 放错位置**：写成 `-i in.m4a -ss 4800 -t 1200 out.m4a`，
   这是"输出侧 seek"—— ffmpeg 会**从头解码 80 分钟音频再丢掉**。
   发到第 9 个分片时就要解码 160 分钟。改成**输入侧** `-ss 4800 -t 1200 -i in.m4a`
   后是瞬时定位：实测 600 秒素材切 10 个分片，总耗时从"分钟级/卡死"降到 **4.7 秒**。
2. **`subprocess.run(timeout=)` 在 Windows 上不可靠**：超时后 CPython 会
   `kill()` 再 `communicate()` 收尾，而**只要孙子进程还握着管道句柄，这一步永远不返回**。
   实测就是这样：ffmpeg 没被清掉、python 永远卡在收尾。

**规范**：

* 统一走 `run_ffmpeg(cmd, timeout, tag)` / `run_capture(cmd, timeout, tag)` 两个助手：
  用 `Popen` + `p.wait(timeout=)`，**stdout/stderr 直接 `DEVNULL`（不建管道）**，
  超时即 `kill()` + 回收；`run_capture` 要拿输出时把 stdout 写到**临时文件**而不是管道。
* 所有 ffmpeg 调用都带 `-nostdin -loglevel error` 与硬超时（切分 300s、预览抽音 120s）。
* **2026-10-15：不再有 ffprobe 调用。** 报时长改由 `ffprobe_duration()` 跑
  `ffmpeg -hide_banner -i <file>` 并解析 stderr 上的 `Duration:`（该命令因没给输出
  文件而返回 1，所以走 `run_capture_stderr(..., ok_rc=(0,1))`，仍是临时文件不是管道）。
  去掉 ffprobe 是因为它有 161MB，而只干这一件事 —— 自带运行时因此减半。
* 切分后再校验：产物必须**存在且非空**，否则立刻抛错 —— 空分片会静默变成空转录。

### 第三轮的三个附带发现（都要记住）

**发现一：`warning` 存在两种合法措辞，且有引号/无引号两种写法。**

实测分布：`428` 条带引号的长版、`113` 条**无引号**的另一版、
`11` 条弱化版、`4` 条错别字版。因为守卫当初只写了"带引号"的正则
（`^warning:[ \t]*"(.*)"`），**79 个文件被误报成"缺 warning"**。
教训：校验语料里的"人类文本字段"时，正则要么两种引号形态都吃
（`^warning:[ \t]*"?(.*?)"?[ \t\r]*$`），要么先规范化再比较。

**发现二：28 个"占位符元数据"文件来自一批伪造 bvid 的早期导入。**

`title: ""` + `date: "1970-01-01"` + `duration: ""`，`status: "transcribed"`。
回源 B站 `view` API 逐个核对：**26 个返回"啥都木有"（视频不存在），
2 个返回"请求错误"（bvid 不合法）** —— 即元数据**永远无法恢复**。
这些文件的特征说明它们不是正常采集产物：

* 正文只有 580–1200 字（正常转录稿数万字）；
* 全篇**繁体汉字、词间加空格**（zh-TW 自动字幕风格，与语料其余部分不符）；
* 同一段文字被复制到 **3–15 个不同 bvid** 上（15 个副本共享同一段 585 字）；
* 正文 H1 本身就是空的（`#\n## 语音转录`）。

处置：**只做"去谎言"**（R14：占位日期清空，不猜日期），内容保留，
lint baseline 登记，是否删除由用户裁决。**不要**用"看起来像的日期"去填。

**发现三：守卫自己也会误报，所以必须做负向自检。**
`corpus_lint_selftest.py` 用临时目录造 19 类缺陷样本，
逐条断言"规则确实触发过了"。**没见过失败的守卫不算守卫。**

### 附一｜换行符：先搞清事实，再谈"归一化"

第一次写占位文件时只对正文做了 `\n` → `\r\n`，frontmatter 是另一个字符串，
**留下 8 个裸 LF**。

**顺手全库点了一遍，事实和一直以来的说法不一样**（`_eol_scan.py`，只读）：

| | 数量 |
|---|------|
| md 总数 | 3714（主库）/ 3713（镜像库，另 1 个 `no-git-operations.md`） |
| **LF-only** | **403** |
| 混合换行 | **0** |
| BOM | **0** |

也就是说 **"语料是 CRLF-only"这句话是错的**（约 89% 是 CRLF，403 个是纯 LF）。
这 403 个不是第四轮改出来的：采集器新写的稿子和本轮重转录的 13 个文件都是 CRLF，
LF 那批是更早的批次。两库对这批文件的处理完全一致，kb-mcp 也没报问题。

> **规则修正**：R15 的本意是"**编辑文件时保持它原有的换行风格**"，不是"把所有文件都
> 改成 CRLF"。自己**新建**文件时跟随多数派 CRLF；**不要为了整齐去批量改写 403 个
> 文件**（纯噪音 diff，且属于 R 系列明确反对的"为整齐而重写"）。

R15 的补强断言（对自己新建/改写的文件）：

```python
assert text.count("\n") == text.count("\r\n")     # 不允许混行
```

另外**先归一化到 `\n`，最后一次性转 `\r\n`**，不要对多个片段分别做替换。

### 附二｜和"只认引号"是同一类 bug（这次反向犯了一次）

第三轮的教训是"正则只认**带引号**的 `warning`"，导致 79 个误报。

把合法的 `type: "dialogue"` 判成"缺 type"。同一条规则的两次镜像错误。

修正：`RE_TYPE = re.compile(r'^type:[ \t]*["\']?(\w+)["\']?[ \t\r]*$', re.M)`

> 通用纪律：**凡是从 frontmatter 取值做等值比较，正则必须同时容纳
> 带引号与不带引号两种写法**；否则屏幕上会多出一批"看起来像缺陷"的假象，

### R29｜执行命令**一律走 Git Bash**，不用 PowerShell

**约定**

- 运行环境 = `C:\Program Files\Git\bin\bash.exe`（本机 `bash 5.3.15` / `git 2.56.0`）。
- **不写 PowerShell 逻辑**：不用 `Select-String`、不写 `$var`、不用 `Tee-Object`。
- 唯一例外是"启动器"：DSH 的命令工具本身是 `pwsh`，它只负责把 bash 拉起来。
  命令体里**只允许**形如 `& "C:\Program Files\Git\bin\bash.exe" <脚本> [参数]`。
- **非平凡命令先落盘成 `.sh` 再调用**，不要把多条命令内联进命令参数。

**为什么（不是洁癖，是踩过两次）**

外层 PowerShell 会**抢先解析** `|` `>` `;` `$` `&`，于是脚本"看起来坏了"，其实是外壳
把参数改坏了：

| 实际发生的 | 现象 |
|---|---|
| `... \| tee /c/Users/...log` | 被当成 PowerShell 的 `Tee-Object`，报 `C:\c\Users\...` 路径不存在 |
| `awk '{print $1}'` | `$1` 被 PowerShell 吃掉 → awk 报语法错误 |

另外 PowerShell 5.1 的 `Set-Content` / `Out-File` / `>` 会写 UTF-16LE 或 CP936
（第一轮 2961 文件事故的根因，见 R1/R2/R26）——这是**不信任它写文件**的理由。

**前置条件（很容易被误判成"环境坏了"）**

MSYS2 运行时启动时**必须创建命名管道**，受限沙箱会拒绝：

```
bash.exe: *** fatal error - couldn't create signal pipe, Win32 error 5   (退出码 0xC0000142)
```

→ **Git Bash 只能在完全访问（danger-full-access）下运行**。
`git.exe` 是原生 Windows 程序，**不受影响**，受限模式下照样能用 ——
"bash 挂了"≠"git 挂了"，别混为一谈。

**落点**：`SKILL.md` 的 Prerequisites / R29 / 命令块；语料库 `memory/shell-git-bash-only.md`。

### R30｜识别引擎改为**本机 SenseVoice**，在线 Whisper API 已丢弃

**新构成**

| 部件 | 位置 | 说明 |
|---|---|---|
| CLI | `scripts/sensevoice_asr.py` | stdout **只出正文**，诊断走 stderr；退出码 0/2/3/4/5 |
| 运行时 | `scripts/.venv/` | `sherpa-onnx 1.13.8` + `numpy 2.5.3` |

模型来自**用户已备好的 DSH 插件目录**。第六轮曾因搜索范围只覆盖 `Documents` /
`AppData\Local` / `AppData\Roaming`（漏了 `~/.dsh`）而**重复下载了 228MB**，
属于"没查到就动手"的错误，已删除重复副本。

**调用方式**：`bilibili_transcribe.py` 把 CLI 当"外部可执行文件"（与 ffmpeg 同样处理），
因此采集器**仍然只用标准库**；`transcribe_file()` / `transcribe_long_audio()`
公开签名不变，内部改为子进程调用，**不再按 25MB 分片**。

**为什么换（同一视频实测对照，`BV19nA8zwEoU`，213s，两稿 1572/1579 字）**

| 对比 | Whisper（旧） | SenseVoice（新） |
|---|---|---|
| 标点 | **完全没有**，只有空格 | 完整 `，。？！` |
| 实事求是 | 「实质求是」✗ | ✓ |
| 限制调控 | 「限制调换」✗ | ✓ |
| 修复信用 | 「修复新用」✗ | ✓ |
| 公立教育 | 「公益教育」✗ | ✓ |
| 速度/成本 | API 往返 + 凭据 + 体积上限 | CPU int8，RTF≈0.10（约 10 倍实时），离线免费 |

**两个必须记住的坑（都已修，改动此逻辑时务必保留）**

① **`VAD.max_speech_duration` 不生效。** 设了 20s，213.6s 连续讲话仍只返回 **1 段**。
若直接送识别，SenseVoice 约 30s 的有效窗口会**静默截断**——不报错，只是后半段没了。
处置：CLI 内自建 `enforce_max_segment()`（默认 20s，在静音点切开）。

② **VAD 的 `SpeechSegment.start` 已经削掉起始音节。** 同一句话 Whisper 转出
「**没钱人**就爹妈带着玩」，VAD 切片后 SenseVoice 只得到「些人就爹妈带着玩」——
开头两个字**永久丢失**。处置：`pad_segments()` 给每段前后补静音余量
（默认 0.25s，用相邻边界夹紧防止重叠；实测相邻 8-gram 重复 = **0**）。

③ **VAD 的环形缓冲必须按音频长度给足。** 固定给 60s 时，对「几乎没有静音」的讲话
（独夫之心的视频基本如此）VAD 会把整段攒在缓冲里，原生层便自行扩容并往 stderr 打
`circular-buffer.cc: Overflow! ...`。它虽写着 `No data loss!`，但这是**原生层绕过
Python 日志**的输出，会把 `--quiet` 的干净 stderr 弄脏，而且「先复制再翻倍」的扩容
代价不可控。处置：`_new_vad()` 按 `len(samples)/sr` 一次性给足（上限 2 小时）。
内存提醒：float32 每样本 4 字节，1 小时音频的缓冲约 230MB。

**环境层的两个意外**（换机器时会再遇到）

- `sherpa-onnx 1.13.8` **不再依赖 numpy** → 需手动 `pip install numpy`，
  否则 `ModuleNotFoundError: No module named 'numpy'`。
- 该版本**没有 `sherpa_onnx.read_wave`** → 用标准库 `wave` + numpy 自己读
  （`fetch_sensevoice_model.py` 的 `verify()` 也因此改过）。

**顺带修掉的日志缺陷**：`daily_scan.py` 的 `log()` 用裸 `print()`，某标题含 `U+2011`
时抛 `UnicodeEncodeError: 'gbk' codec can't encode character '\u2011'`，
异常被"每条视频"的 `except` 捕获 → **已经成功落盘的视频被记成 `ERROR`**。
两道防线：模块级 `reconfigure` 两个流（UTF-8 + `errors="replace"`）
+ `log()` 内 `except UnicodeEncodeError` 降级写。
**纪律：判断采集成功以磁盘文件为准，不要只信日志的 OK/ERROR。**

## 十八、第七轮（2026-10-09 深夜）：R28 那条鱼又游回来了

### 起因

换成本机 SenseVoice 后跑当天（10-09）的采集：5 条全部成功、两库零分歧、
`kb verify` 干净。但守卫紧接着报出**新缺陷**：

```
NEW REGRESSIONS -> FAIL  (1)
  语料根目录存在杂散文件                1
       - <root> MEMORY.md.bak
```

### 事实

* 该文件出现在**主库**根目录，228878 字节、3758 行 —— 正是本次采集**写入前**的索引快照；
* 但它的 mtime 显示 `22:35`，而采集是 `23:43` 跑的。原因是 `shutil.copy2()` 会连源文件的
  mtime 一起复制，于是备份"看起来"比实际产生时间早了 68 分钟。
  **mtime 不能用来判断备份是什么时候产生的**；
* 10-08 的 R28 清理清单里**就有 `MEMORY.md.bak` 这个名字**：那次把文件移走了，
  却没有碰产生它的那一行代码 —— 所以它今天原封不动地又长了出来。

### 根因：R23 的又一次复现

`daily_scan.py` Step 5：

```python
bak_path = mem_path + '.bak'        # mem_path 就在语料根目录里
shutil.copy2(mem_path, bak_path)    # → 杂散文件落进语料根，直接撞 R28
```

"把症状清掉"不等于"把写入路径修好"。规则写在文档里（R28）、守卫也在盯着
（`lint_stray()`），但**产生文件的那一行**没改，下一轮它必然再犯 —— 这正是 R23 的原话。

### 处置

* `daily_scan.py` 改为把备份写到语料根**之外**，并滚动保留最近 10 份：

```python
bak_dir  = os.path.join(BASE_DIR, '_memory_backup')
bak_path = os.path.join(bak_dir, 'MEMORY_%s.md.bak'
                        % datetime.now().strftime('%Y%m%d_%H%M%S'))
shutil.copy(mem_path, bak_path)     # 用 copy 而非 copy2：mtime = 备份时间
# 只保留最近 10 份，避免 BASE_DIR 无限增长
```

* 本轮那个杂散文件**没有删**，按 R28 惯例移出到 `BASE_DIR/_memory_backup/` 留作安全网
  （它是一份完整的 3758 行快照，命名为 `MEMORY_20261009_234303.md.bak`）；
* 原因就地写进代码注释（含"copy2 会带旧 mtime"这条），免得下次再有人以为它是 22:35 的东西。

### 怎么验的

不满足于 `py_compile`：**从真实文件里把那段代码按行切出来直接执行**（不是复制一份来测），
断言三件事 —— 语料根目录多出 0 个文件、滚动后恰好留 10 份、最新备份 mtime ≈ 现在。
第一版因为切分起点没限定（同一个 `open(mem_path...)` 在第 123 行也出现过），
抽出了**空区块**却照样"跑通"，靠 `assert block.strip()` 才暴露出来。
**测试脚本自己也会撒谎**，所以抽完必须先断言非空、且含关键字。

### 第七轮踩坑速查

| 现象 | 根因 | 处置 |
|---|---|---|
| 守卫报"语料根目录存在杂散文件 `MEMORY.md.bak`" | `daily_scan.py` 把备份写在语料根内 | 备份移到 `BASE_DIR/_memory_backup`（R28） |
| 备份 mtime 比采集时间早一个多小时 | `shutil.copy2` 连源文件 mtime 一起复制 | 改用 `copy`；**别用 mtime 推断备份产生时间** |
| 上个月刚清掉的杂散文件又出现了 | 只清了症状，没改产生它的那一行（R23） | 清症状时**必须同时定位写入方** |
| 测试"通过"其实什么都没测 | 切分起点没限定，抽出空区块 | 抽取后先断言非空 + 含关键字 |

### 验收（第七轮）

* 主库根目录只剩 `.md`，镜像库只剩 `.md` + 两个状态文件；
